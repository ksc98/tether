# Fork notes: building, installing, debugging

This fork (`ksc98/tether`, branch `kyle`) carries the Shortcuts clipboard
intents and the Bluetooth clipboard push ([BLUETOOTH-CLIPBOARD.md](BLUETOOTH-CLIPBOARD.md)).
Upstream is `zackb/tether`. This file is the working manual for the fork.

## Branches

- `kyle`: everything, including fork-only tooling (CI workflow, justfile,
  sideload entitlements, these docs). CI builds from here.
- `shortcuts-clipboard-intents`: the upstreamable intents feature alone.

## Desktop side

```
just install
```

Builds an Arch package (`tether-git`) from the current checkout with
`makepkg`, installs it with `pacman -U`, and restarts `tetherd`. The PKGBUILD
in the repo points at upstream's git; the recipe rewrites its `source=` to
`git+file://<checkout>#branch=<current>`, so commit before installing.
`--ask 4` answers the `tether-bin` conflict prompt on the first install.

Plain builds for a compile check: `cmake --preset release && cmake --build
--preset release` (binaries under `build/release/`).

A client spawns `tetherd` on demand. After an install, `pkill -f '^tetherd'`
then any `tether` command starts the new binary. The log is
`$XDG_STATE_HOME/tether/tetherd.log`.

## iOS side

### Why the app builds in CI

Shortcuts finds an app's actions through `Metadata.appintents`, generated by
Xcode's `appintentsmetadataprocessor`. Nothing on Linux produces it, so
`.github/workflows/ios-sideload.yml` builds the app on a `macos-26` runner on
every push to `kyle` that touches `apple/`, ad-hoc signs it with
`apple/Tether-sideload.entitlements`, drops the Share Extension (see below)
and uploads `Tether.ipa`.

```
just ios-install        # newest successful CI IPA → xtool install --usb
```

`xtool install` re-signs with the personal team: the bundle becomes
`XTL-<id>.net.jeedup.Tether`, a separate app from the App Store Tether with
its own pairing. Claude Code's sandbox blocks the usbmuxd socket, so the
install runs unsandboxed.

The sideload build has no App Group and no Share Extension. xtool provisions
App Groups only with Apple-ID login (the ASC API key path skips it silently),
and a re-signed extension would land in a different keychain group from the
app anyway. The App Intents run in the main app process and are unaffected.

### Type-checking on Linux before pushing

Compile the app sources against the iOS SDK without Xcode, so a broken push
never reaches CI:

1. A scratch `darwin.artifactbundle` beside the real one
   (`~/.config/swiftpm/swift-sdks/darwin.artifactbundle`): symlink
   `Developer/` and `toolset/`, copy `info.json` and `swift-sdk.json`, and a
   `toolset.json` with the shared xros `-target` removed and no empty
   `cCompiler` entry (SwiftPM rejects one). The shared file stays as it is.
2. A scratch SwiftPM package with an executable target over a *copy* of
   `apple/Tether` (a script strips `#Preview` blocks, the previews macro
   plugin does not exist on Linux), depending on
   `apple/TetherFramework` by path, with `swiftLanguageMode(.v5)`,
   `.defaultIsolation(MainActor.self)` and the approachable-concurrency
   upcoming features to match the Xcode target.
3. `swift build --swift-sdk arm64-apple-ios --swift-sdks-path <scratch>`.

Capture the build output in a variable and test for `Build complete` before
committing. A pipeline into `head` hides the compiler's exit status.

### Local xtool build (unfinished)

`apple/DevBuild/` is a SwiftPM package that xtool can build into an `.app`
without the runner: a library product named in `xtool.yml`, the sources
copied in by `sync.py`, and `Metadata.appintents` taken from a CI IPA and
listed under `resources:` so Shortcuts still lists the actions. It is blocked
on the same xros toolset pin. xtool reads SwiftPM's config from
`$XDG_CONFIG_HOME/swiftpm`, so a fake `XDG_CONFIG_HOME` whose
`swiftpm/swift-sdks` holds the clean bundle and whose `xtool` links to the
real `~/.config/xtool` is the next thing to try. `HOME` has to stay real:
xtool's launcher script and swiftly live under it.

## Debugging on the phone

- The app's own trace: Settings → Bluetooth Clipboard → **Log**. This is the
  primary tool. `idevicesyslog` shows framework lines from the process but
  not the app's `os_log` calls on iOS 27.
- Screenshots from Linux: `pymobiledevice3 mounter auto-mount` once per
  boot, `sudo ~/.local/bin/pymobiledevice3 remote tunneld` in the
  background (sudo needs the full path), then
  `pymobiledevice3 developer dvt screenshot out.png --tunnel ''`.
- Link traffic on the desktop: `sudo btmon -t`, filter on `ATT:`. The
  periodic `Read Request/Response len 11` pairs are tetherd's own link check.
- When tailing anything through a pipe from a background shell, use
  `stdbuf -oL` on every stage, otherwise the output sits in a buffer until
  the process exits.

## Bluetooth setup on this machine

Both are host-level and survive package upgrades:

- `/etc/systemd/system/bluetooth.service.d/experimental.conf` runs
  `bluetoothd --experimental`, which ANCS needs. It has to be in place before
  pairing, or the bond has no LE half.
- `tether-btclass@hci0` sets the Class of Device to A/V Hands-Free after
  every `bluetooth.service` start, because iOS offers the Messages and
  Contacts toggles only to that class.
